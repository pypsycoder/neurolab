# НейроЛаб — управление проектом

**Статус:** утверждён для исследовательского режима  
**Дата:** 2026-09-13

## Контекст запуска

- **Рабочая юрисдикция:** Российская Федерация.
- **Режим до отдельного решения:** исследование и инженерные интеграции только
  на публичных и синтетических данных.
- **Единый ответственный на этом этапе:** владелец проекта (пользователь).
- **Не допускается:** подключение реальных пациентов, получение/обработка их
  данных, предоставление клинических рекомендаций и запуск пациентского UI.

## Роли и обязательные решения

| Роль | Ответственность | Статус назначения |
|---|---|---|
| Владелец продукта | Ценность сценариев, бюджет, приоритеты, решения go/no-go | Временно: владелец проекта (пользователь) |
| Клинический владелец (нефролог) | Intended use, медицинский контент, красные флаги, клиническое одобрение | Не назначен; клинический контур заблокирован |
| Владелец данных / DPO | Законность обработки, согласия, минимизация и сроки хранения данных | Временно: владелец проекта, только синтетические данные |
| Владелец ИБ | Модель угроз, доступы, секреты, аудит и реакция на инциденты | Временно: владелец проекта, только исследовательский контур |
| Технический владелец | Архитектура, качество кода, CI/CD, надёжность интеграций | Временно: владелец проекта |
| Эксплуатационный владелец | Поддержка, SLO, мониторинг, резервное восстановление и rollback | Временно: владелец проекта; production не создаётся |

Один человек может занимать несколько ролей только при явном согласовании; роль
клинического владельца нельзя заменить решением модели или инженерной команды.
Временное совмещение не наделяет владельца проекта клиническими полномочиями,
если он не назначен и не действует как соответствующий специалист.

## Решения, требующие утверждения до клинического контура

1. Целевая юрисдикция, организация-оператор и основания обработки данных.
2. Первый ограниченный use case и группа пользователей.
3. Клинический владелец и процедура рецензирования контента.
4. Допустимые источники знаний и срок их пересмотра.
5. Условия пилота, KPI, критерии остановки и процесс рассмотрения инцидентов.

## Правило принятия решений

Архитектурные решения фиксируются в `docs/adr/` до реализации существенного
изменения. Решения, затрагивающие пациента, клинический контент, данные,
интеграции или доступы, должны содержать владельца, оценку риска, альтернативы,
дату пересмотра и явное решение.

## Минимальный цикл изменения

```text
Запрос → оценка риска → решение/ADR → реализация в test → проверки → review
       → нужное одобрение → ограниченный выпуск → мониторинг → журнал результата
```

Ни один агент не утверждает собственное клинически значимое изменение и не
выпускает его в клинический контур самостоятельно.
