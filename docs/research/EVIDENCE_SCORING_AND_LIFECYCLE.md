# Оценка доказательств и замкнутый цикл НейроЛаба

## Принцип

Не существует одного «рейтинга статьи». Один источник может содержать хорошую
теорию, слабое измерение и полезную implementation-идею одновременно. Поэтому
система хранит источник отдельно от его проверяемых **утверждений** (claim) и
оценивает каждое утверждение по нескольким независимым осям. Неопределённость
не подменяется низким баллом: она явно маркируется как `unknown`.

Это сохраняет теорию как инвестицию в будущее, но запрещает строить на ней
необратимые production-решения до появления реалистичных доказательств.

## Карточка утверждения

Каждое существенное утверждение после чтения полного текста получает:

| Ось | Вопрос | Шкала |
|---|---|---|
| Концептуальная обоснованность | Метод непротиворечив, формально описан, связан с прежними знаниями? | 0–1 + уверенность |
| Качество эмпирических доказательств | Есть корректный эксперимент, baseline, измеримые ограничения? | 0–1 + уверенность |
| Воспроизводимость | Есть публичные код, данные, окружение, инструкции и независимая репликация? | 0–1 + уверенность |
| Реализуемость сейчас | Доступны ли требуемые вычисления, интерфейсы, лицензии, стоимость и компетенции? | 0–1 + перечень зависимостей |
| Архитектурная ценность | Влияет на глобальную архитектуру, подсистему, компонент или фичу? | multi-label |
| Независимость подтверждения | Подтверждение получено не только авторами/вендором? | 0–1 |
| Риски и границы применимости | Какие режимы отказа, допущения и неизвестные факторы? | структурированный список |

Оценка источника (`peer-reviewed`, preprint, документация вендора, репликация,
производственный кейс) — лишь один из входных сигналов и не заменяет эту
карточку.

### Уровни зрелости утверждения

1. `hypothesis` — идея или предположение без проверяемого метода.
2. `formal_or_method` — формальная модель/алгоритм с достаточно точным
   описанием; может быть ценной для эксперимента.
3. `simulated_or_benchmarked` — проверка на симуляции либо benchmark.
4. `prototype` — воспроизводимый прототип с кодом и инструкциями.
5. `replicated` — независимое воспроизведение или сопоставимое подтверждение.
6. `operational` — наблюдаемый опыт эксплуатации с измеренными границами.

Теоретическая модель на уровне `formal_or_method` не удаляется и не получает
штраф «за теорию». Она получает маршрут `research_experiment`, если не
противоречит известным физическим, вычислительным, правовым или интерфейсным
ограничениям. Для production baseline требуются как минимум `prototype`,
достаточная реализуемость и воспроизводимость; для изменения критического
контура — `replicated` либо явно одобренное человеком исключение.

Так исключается «проектирование телепортатора»: эффектная гипотеза без
доступного механизма, измерения и достижимых зависимостей остаётся в
watchlist/research, а не превращается в обязательный компонент системы.

## Правила принятия решений

Из вектора оценок выводится не усреднённый балл, а одна из четырёх полос:

- `watchlist` — интересно, но пока слишком мало проверяемых оснований;
- `research_experiment` — допустимо проверить в synthetic sandbox с заранее
  заданным бюджетом и критерием остановки;
- `implementation_candidate` — можно сформировать review-only ТЗ для Code
  agent в отдельном worktree;
- `production_candidate` — только после независимой проверки, безопасности,
  лицензий и отдельного человеческого решения. В текущем проекте эта полоса
  не означает клиническое применение.

Полоса выбирается по минимальным условиям по каждой оси, а не суммой баллов.
Все оценки должны содержать ссылку на evidence и версию правила; ручная
переоценка не удаляет исходную автоматическую оценку.

## Полный цикл

1. **Стартовое ТЗ-0.** Человек утверждает короткий research charter: проблему,
   ограничения, допустимый бюджет, целевые уровни архитектуры и критерии
   успеха. Это не финальное ТЗ на код.
2. **План поиска.** Планировщик формирует несколько bounded вопросов: новую
   архитектуру, конкретный компонент, известный дефект или сравнение решений.
   Он не имеет доступа к shell, Git, секретам или clinical data.
3. **Сбор и проверка.** Discovery сохраняет provenance и метаданные. Затем
   разрешённый full-text контур извлекает claims, методы, ограничения и
   артефакты; evaluator заполняет карточки утверждений и дедуплицирует их.
4. **Накопление и coverage gate.** Корпус должен быть сбалансирован по уровням
   архитектуры, независимым подтверждениям и зрелости. Пока gate не пройден,
   он возвращает следующий research gap, а не ТЗ Code agent.
5. **Синтез ТЗ-1.** Только из структурированных claims и evidence формируется
   review-only многоуровневое ТЗ: решения, альтернативы, допущения, зависимости,
   измеримые acceptance criteria, риски и rollback. Человек утверждает scope.
6. **Разработка.** Code agent работает в одноразовом worktree по утверждённому
   ТЗ-1, возвращает diff, тесты, ограничения и receipt; не делает merge/push/deploy.
7. **Независимая проверка и решение.** Evaluator повторяет релевантные тесты,
   проверяет policy и evidence. Человек выбирает: сохранить в продукт,
   исправить, выделить удачную «запчасть» в библиотеку либо отбросить.
8. **Обучающий feedback.** Итог, метрики и причина решения связываются с
   claims и ТЗ. Planner получает только эту структурированную обратную связь и
   формирует следующий вопрос поиска; цикл возвращается к пункту 1 или 2.

## Полнотекстовые PDF

PDF нужен для extraction/проверки claim, а не для доказательства по одному
заголовку. Перед загрузкой проверяются: законность доступа и лицензия, точный
URL, MIME/размер/хеш, отсутствие перенаправлений за allowlist и соответствие
теме. Автоматически допустимы открытые источники с понятными правами (например,
arXiv либо другой явно открытый архив). Publisher PDF с неясными правами не
копируется в корпус: сохраняются citation, provenance и статус `license_unknown`
для ручного решения.

Сырой PDF и извлечённый текст считаются недоверенными данными: они не могут
управлять инструментами или становиться инструкциями агенту. Хранение требует
отдельной retention/access policy; в основной research БД остаются хеш,
лицензия, ссылка и структурированные claims. Никакие clinical/patient данные
в этот контур не добавляются.

Первый реализованный verifier принимает только modern arXiv ID, уже найденный
`source_key` и явную совместимую лицензию (`CC-BY-4.0`, `CC0-1.0` или
`PUBLIC-DOMAIN`). Он не принимает URL из аргумента. Переходы, иной MIME-тип,
не-PDF подпись, размер больше 25 MiB, более 100 страниц и текст более
1 000 000 символов означают отказ. После успешного extraction сохраняется
только receipt; PDF и raw text не удерживаются. Запуск остаётся ручным и
одноразовым:

```bash
docker compose --profile research run --rm --entrypoint python research \
  /app/scripts/verify_open_access_pdf.py \
  --source-key <64-char-source-key> --arxiv-id <id> --license CC-BY-4.0 --persist
```

На этом этапе автоматического full-text запуска нет: discovery ещё не
предоставляет проверенный license record для конкретного arXiv-документа.
Такой документ должен сначала получить явную license-проверку, а затем
отдельный reviewer создаёт claims с номером страницы и уровнем зрелости.

Claim, созданный разрешённой моделью, хранится как `needs_review`; только
человек может сделать его `reviewed`. Теоретическое утверждение разрешено
сохранить с высоким conceptual support, но policy ограничивает его полосой
`watchlist` или `research_experiment` до появления прототипа и проверки.

После human review для claim можно проверить связанный публичный репозиторий
строго через GitHub API: только идентификатор `owner/repository`, без URL и без
скачивания кода. Receipt фиксирует лицензию, ветку, README, тестовые пути,
manifest окружения и data-пути. Это ещё не означает, что результаты
воспроизведены: запуск кода, данные и benchmark будут отдельными opt-in
этапами. Связывание repository receipt с model claim запрещено — нужен
`reviewed` claim, относящий этот репозиторий к источнику.
