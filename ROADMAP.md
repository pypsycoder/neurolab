# НейроЛаб — дорожная карта

**Версия:** 0.1  
**Создана:** 2026-09-13  
**Назначение:** от проверяемых интеграций GigaChat, gpt2giga, Hermes,
OpenHands, LangGraph и MCP — к безопасной клинической системе поддержки
пациентов на гемодиализе.

## 1. Цель, архитектура и границы

НейроЛаб — инженерно-исследовательская среда, которая исследует агентные
системы и решения для помощи пациентам на гемодиализе, помогает разрабатывать
код и превращает только проверенные компоненты в отдельный пациентский продукт.

```text
Исследовательско-инженерный контур
GigaChat/gpt2giga → LangGraph Supervisor → Hermes / OpenHands / MCP-инструменты
                                      ↘ репозиторий, тесты, изолированные worktree

Клинический контур
Пациент/врач → API и клинический workflow → ограниченная модель/база знаний
                                      ↘ аудит, мониторинг, эскалация специалисту
```

Пациентский контур не получает shell, браузер, Git, репозиторий, произвольный
MCP или право менять код. Он не ставит диагноз, не назначает лечение и не
заменяет врача. При опасных симптомах он следует утверждённому маршруту
эскалации, а не пытается дать медицинское заключение.

## 2. Общие принципы готовности

- Каждый этап имеет измеримый результат, тесты и явное решение `go / no-go`.
- До клинической валидации используются синтетические, обезличенные и законно
  разрешённые данные; секреты и идентификаторы пациентов в репозиторий не
  попадают.
- Медицинские утверждения имеют первоисточник, дату проверки, клинического
  владельца, историю изменения и срок пересмотра.
- Модель не является источником истины: пороги, протоколы и маршрутизация
  хранятся в версионируемых правилах и утверждённой базе знаний.
- Агенты работают с минимальными правами, ограничением времени/затрат/циклов,
  аудитом и возможностью немедленной остановки человеком.
- Технический успех сам по себе не разрешает работу с пациентами: требуются
  клиническое, правовое, ИБ- и эксплуатационное одобрения.

## 3. Этапы

### Этап 0. Инициация и контроль проекта

**Цель:** подготовить воспроизводимую среду и правила принятия решений.

1. Назначить владельцев: продукт, клиническая безопасность, ИБ/данные,
   инженерия и эксплуатация.
2. Зафиксировать разрешённые сценарии и запреты для исследовательского,
   инженерного, врачебного и пациентского контуров.
3. Подготовить репозиторий, CI, шаблоны ADR, реестр рисков, трекер решений,
   политику секретов и раздельные окружения `dev/test/prod`.
4. С юристом, DPO и ИБ определить применимые правила персональных данных,
   медицинского ПО и клинической ответственности для целевой юрисдикции.

**Критерии готовности:** владельцы и границы утверждены; есть реестр рисков,
изолированные окружения и секреты вне репозитория.

### Этап 1. Технические интеграционные пробы

**Цель:** доказать работоспособность компонентов по отдельности и в простой
сквозной цепочке, без пациентских данных.

#### 1.1. GigaChat

Проверить аутентификацию, доступные модели, лимиты, потоковые ответы, ошибки,
квоты/стоимость и безопасное журналирование. Добавить contract- и
negative-тесты для таймаутов, неверной авторизации и исчерпания лимита.

#### 1.2. gpt2giga

Развернуть адаптер в изолированном окружении. Сверить совместимость форматов
запросов, structured output и tool calls (если поддерживаются), повторы,
таймауты и безопасную деградацию при сбое провайдера.

#### 1.3. Hermes

Выбрать конкретную версию/проект и определить его роль: исследователь, а не
клинический валидатор. На открытых источниках проверить поиск, сбор ссылок,
извлечение тезисов, дат, ограничений и степени уверенности.

#### 1.4. OpenHands

Запустить в одноразовом sandbox/worktree с минимальными правами. Выполнить
задачу «исправить маленькую ошибку → запустить тесты → сформировать diff».
Запретить доступ к продакшен-ключам, произвольной сети и учётным данным.

#### 1.5. LangGraph

Собрать минимальный граф:
`задача → планировщик → один агент/инструмент → валидатор → отчёт`.
Проверить сохранение состояния, checkpoint, возобновление после сбоя, лимит
итераций, отмену и трассировку.

#### 1.6. MCP

Подключить только тестовые серверы: файловый, документация/поиск и Git в
тестовом репозитории. Для каждого инструмента описать контракт, схему
параметров, разрешения и негативные тесты: отказ доступа, ошибочный вызов,
prompt injection из недоверенного результата.

#### 1.7. Сквозной smoke test

Выполнить сценарий: «найти источники → спланировать изменение учебного кода →
внести изменение в worktree → запустить тесты → вернуть отчёт с ссылками и
diff». Артефакт должен быть повторяемым.

**Критерии готовности:** автоматические smoke/integration-тесты зелёные;
права и секреты изолированы; у каждой интеграции есть trace, отчёт и безопасный
отказ.

### Этап 2. Контролируемый исследовательский и инженерный контур

**Цель:** сделать агентов полезными, но управляемыми человеком.

1. Разделить роли LangGraph: supervisor, исследователь, разработчик,
   тестировщик, reviewer, synthesizer. Для каждой установить допустимые
   инструменты, лимиты циклов, времени и затрат.
2. Создать research pipeline: поиск → первоисточники → извлечение цитат и
   ограничений → сопоставление источников → отчёт с пробелами и датой проверки.
   Хранить промежуточные артефакты; не выдавать неподтверждённый клинический
   вывод за факт.
3. Создать engineering pipeline: задача → план → worktree → правки → format/
   lint/type-check → unit/integration/security tests → review → ручное
   утверждение merge. Агент не сливает код и не деплоит prod сам.
4. Защититься от инъекций и опасных вызовов: веб-страницы и документы — это
   недоверенные данные, параметры MCP валидируются схемой и политикой.
5. Ввести наблюдаемость: ID запуска, версии модели/промпта/графа/инструмента,
   расходы, latency, ошибки, решение валидатора и ссылку на артефакты.

**Критерии готовности:** эталонный набор исследовательских и кодовых задач
достигает заданных метрик; опасные вызовы блокируются; у каждой правки есть
цепочка «задача → diff → тесты → review».

### Этап 3. Клиническая постановка и база знаний

**Цель:** выбрать ограниченный и проверяемый первый клинический сценарий.

1. Совместно с нефрологами выбрать один узкий use case: например, объяснение
   утверждённой памятки, подготовка вопросов к диализу или навигация по
   процедуре. Не начинать с диагностики, терапии или дозировок.
2. Утвердить контент-процесс: источники, авторы, рецензенты, дата редакции,
   уровень доказательств, аудит и срок пересмотра.
3. Описать клинические границы и красные флаги. Для каждого риска нужны
   утверждённый текст, маршрут эскалации, владелец и тест-кейс.
4. Построить версионируемую RAG-базу только из разрешённого корпуса — с
   ссылками на фрагменты, контролем доступа и отказом отвечать вне покрытия.
5. Создать синтетический safety-набор: типовые вопросы, неполные данные,
   красные флаги, конфликтующие инструкции, инъекции, недопустимые запросы и
   языковые варианты.

**Критерии готовности:** клинический владелец письменно утвердил use case,
контент, границы и эскалации; ответы прослеживаются до источников; красные
флаги покрыты автоматическими тестами.

### Этап 4. Неавтономный клинический прототип

**Цель:** создать отдельный прототип для закрытого внутреннего испытания.

1. Реализовать отдельный API/UI пациентского помощника без доступа к
   исследовательскому и инженерному контурам.
2. Реализовать согласия, минимизацию данных, RBAC, шифрование, сроки хранения,
   экспорт/удаление по применимым правилам и неизменяемый аудит.
3. Реализовать workflow: намерение → проверка покрытия знаниями → ответ по
   утверждённому контенту → safety-проверка → эскалация/отказ. При низкой
   уверенности система не угадывает.
4. Создать clinician review: просмотр и разметка диалогов, корректировка
   контента, обратная связь без скрытого обучения на данных пациентов.
5. Провести threat model, анализ вреда, privacy/security, нагрузочные,
   accessibility и usability-тесты с нужными согласиями.

**Критерии готовности:** safety-набор пройден; критические сценарии верно
эскалируются; нет пути к инженерным инструментам или данным вне полномочий.

### Этап 5. Клиническая валидация и готовность к пилоту

**Цель:** доказать безопасность и полезность в заявленном назначении.

1. Зафиксировать intended use, нецелевые применения, KPI, критерии остановки и
   план клинической оценки.
2. Провести независимую ретроспективную оценку на утверждённых обезличенных
   или синтетических данных: точность, полнота эскалаций, ложные успокоения,
   опасные отказы и справедливость по группам.
3. Провести проспективное внутреннее испытание с наблюдением специалистов; не
   давать системе самостоятельных лечебных полномочий.
4. Получить юридическую, этическую, ИБ- и регуляторную оценку для конкретной
   юрисдикции; установить применимость требований к медицинскому ПО.
5. Утвердить инструкции, обучение, SLO, поддержку, резервное восстановление,
   change control, rollback и постмаркетинговый мониторинг.

**Go/no-go:** пилот возможен только при формальном одобрении клинического
владельца, ИБ, юриста/регуляторного владельца и эксплуатации, без незакрытых
критических рисков.

### Этап 6. Ограниченный клинический пилот

**Цель:** проверить систему в реальном процессе под постоянным контролем.

1. Ограничить когорту, учреждения и сценарии; включить feature flags, kill
   switch и ручную эскалацию.
2. Регулярно анализировать качество, инциденты, эскалации, отказы, дрейф,
   нагрузку и обратную связь пациентов и врачей.
3. Все изменения моделей, промптов, контента, workflow и интеграций проводить
   через оценку риска, регрессионные тесты, клиническое согласование и версии.

**Критерии готовности:** достигнуты заранее утверждённые safety/usefulness
метрики, инциденты укладываются в SLA, независимый обзор рекомендует
масштабирование либо обосновывает остановку.

### Этап 7. Полноценная эксплуатация и улучшение

**Цель:** масштабировать подтверждённые сценарии без ослабления контроля.

1. Расширять учреждения, языки и сценарии только после самостоятельной
   валидации каждого изменения.
2. Поддерживать мониторинг, аудит, управление уязвимостями, переаттестацию
   доступов, резервное восстановление и учения инцидентов.
3. Регулярно переоценивать клинические знания, риски вреда, справедливость и
   регуляторную применимость, а также после существенного изменения модели.
4. Сохранять разделение контуров: код от Dev Agent проходит review, CI,
   security и клиническую валидацию до пациентского контура.

**Критерии готовности:** подтверждённое соответствие заявленному назначению,
прослеживаемость решений и устойчивая эксплуатационная модель.

## 4. Сквозные тесты и обязательные артефакты

| Область | Что проверять | Обязательный артефакт |
|---|---|---|
| Интеграции | контракт, таймауты, отказ, повтор, лимиты | integration tests и trace запуска |
| Агентный граф | checkpoint, отмена, предел итераций, policy | тесты состояний и audit trail |
| Код-агент | изоляция, diff, CI, секреты, опасные команды | worktree, review, результаты CI |
| Исследования | первоисточник, дата, цитаты, конфликт источников | отчёт со ссылками и уверенностью |
| Клиническая безопасность | красные флаги, отказы, эскалации, вред | утверждённый safety-набор и review |
| Данные и ИБ | доступ, шифрование, аудит, удаление, инъекции | threat model и security assessment |
| Эксплуатация | нагрузка, мониторинг, rollback, инциденты | runbook, SLO, учение восстановления |

## 5. Стоп-условия

Остановить автоматическое действие, изолировать релиз и передать владельцу
риска при: утечке/несанкционированном доступе к данным; опасном пациентском
совете или пропущенном красном флаге; выходе агента за полномочия;
неподтверждённом клиническом контенте; обходе аудита; критической уязвимости;
невозможности откатить версию. Возобновление допускается только после
документированной причины, исправления, регрессионной проверки и одобрения.
